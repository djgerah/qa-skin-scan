# Skin Scan — QA Automation Framework

## 1. О проекте

**Краткое описание:**  
Автотесты для серверной части приложения скрининга кожи (SkinScan API). Фреймворк работает по принципу **black-box**: тестируемое приложение запускается отдельно, фреймворк взаимодействует с ним только через REST API (REST Assured) и напрямую через БД (JDBC) — для проверки данных, записанных сервером.

**Покрытие на текущий момент:**
- ✅ Проверка состояния сервера и связности с БД (`/skinScan/check-run`).
- ✅ Регистрация пользователей: успешная (в том числе без email и телефона), повторная (409), невалидный email, короткий пароль, пустой логин или пароль (400).
- ✅ Аутентификация: успешный вход с выдачей JWT (`accessToken` + `refreshToken`), неверный пароль, несуществующий пользователь (401), вход без тела запроса (400).
- ✅ Rate limiting: превышение лимита регистраций и логинов с одного IP (429).
- ✅ Обновление данных пользователя: с валидной авторизацией, без авторизации, с невалидным токеном, с неверным паролем в теле.
- ✅ Смена пароля: успешная смена, вход со старым/новым паролем, неверный старый пароль, короткий новый пароль, попытка сменить чужой пароль (401).
- ✅ Загрузка фотографий: успешная загрузка (202), повторная загрузка с тем же именем (200), неверный формат файла (400), загрузка без авторизации (401), одинаковое имя у разных пользователей (202).
- ✅ Получение фотографий: по id и по имени после завершения асинхронного анализа (200), во время анализа (502), несуществующие id/имя (404), не-UUID id (400), доступ чужого пользователя (403 для id, 404 для имени), список фото (200, у нового пользователя пуст) и без авторизации (401).
- ✅ Проверки в БД: пароль хранится как BCrypt-хеш и обновляется при смене; статус фото доходит до «Анализ завершен».
- ✅ Отчёты Allure с шагами (`@Step`) и человекочитаемыми названиями тестов (`@DisplayName`).

## 2. Стек технологий

**Описание выбранных решений с обоснованием:**

- **Язык:** Java 21 (toolchain задан в `build.gradle.kts`).
- **Тестовый фреймворк:** JUnit 5 (Jupiter). Стандарт де-факто для Java-тестов; поддерживает теги для фильтрации запусков.
- **HTTP-клиент:** REST Assured. Удобный DSL для проверки REST API: статус-коды, JSON-пути, multipart-загрузка файлов.
- **Отчёты:** Allure 2 (allure-junit5 + aspectjweaver). Формирует отчёт с шагами, вложениями и группировкой по фичам.
- **Ожидание асинхронных операций:** Awaitility. Анализ фото выполняется асинхронно и завершается через несколько секунд — Awaitility позволяет опрашивать API или БД до готовности (до 60 секунд, шаг опроса 1 секунда).
- **Работа с БД:** Spring JdbcTemplate (PostgreSQL driver). Прямые запросы к БД для проверки данных, не видимых через API.
- **JSON:** Jackson Databind.
- **Сборка:** Gradle (Kotlin DSL).

## 3. Требования к окружению

Перед запуском убедитесь, что у вас установлены:

- **JDK 21** или новее.
- **Gradle 8+** (или используйте wrapper `./gradlew`).
- **Allure CLI** — для генерации и просмотра отчётов (`allure generate`, `allure serve`).
- **Запущенное приложение SkinScan** на `http://localhost:8080` (см. README backend-проекта). Обязательны две настройки:
  ```bash
  # 1. Секрет для подписи JWT: без него приложение не стартует
  #    (jwt.secret=${JWT_SECRET} не имеет значения по умолчанию; HS256 требует >= 32 байт)
  # 2. Отключение случайных сбоев ML-заглушки: иначе тесты, ожидающие завершения
  #    анализа, падают нестабильно (по умолчанию сбой с вероятностью 5%)
  JWT_SECRET=local-test-secret-key-for-skinscan-tests-only-0123456789 \
  APP_ML_CLIENT_STUB_FAILURE_PROBABILITY=0 \
  ./gradlew bootRun
  ```
- **PostgreSQL** — та же БД, которую использует тестируемое приложение (параметры подключения передаются через `-Ddb.*` или переменные окружения `DB_*`).

## 4. Настройка и запуск

### 4.1 Клонирование репозитория
```bash
git clone <url-репозитория>
```

### 4.2 Параметры подключения
Параметры читаются из системных свойств (`-D...`), затем из переменных окружения; если не заданы — используются значения по умолчанию.

| Параметр | Системное свойство | Переменная окружения | Значение по умолчанию |
|----------|--------------------|----------------------|------------------------|
| Базовый URL приложения | `-Dbase.url` | `BASE_URL` | `http://localhost:8080` |
| JDBC URL БД | `-Ddb.url` | `DB_URL` | `jdbc:postgresql://localhost:5432/skinScan_db` |
| Пользователь БД | `-Ddb.user` | `DB_USER` | `skinScan_user` |
| Пароль БД | `-Ddb.password` | `DB_PASSWORD` | `password` |

В CI параметры переопределяются через переменные окружения. Пример запуска с явными значениями:
```bash
./gradlew test \
  -Dbase.url=http://localhost:8080 \
  -Ddb.url=jdbc:postgresql://localhost:5432/skinScan_db \
  -Ddb.user=skinScan_user \
  -Ddb.password=password
```

### 4.3 Запуск всех тестов
```bash
./gradlew test
```
При необходимости параметры подключения переопределяются (см. 4.2):
```bash
./gradlew test -Dbase.url=... -Ddb.url=... -Ddb.user=... -Ddb.password=...
```

### 4.4 Запуск по тегам
Тесты размечены тегами `smoke`, `regression`, `security` и `db`. Фильтрация через системное свойство `tags` (через запятую):
```bash
./gradlew test -Dtags=smoke
./gradlew test -Dtags=regression
./gradlew test -Dtags=security
./gradlew test -Dtags=db
./gradlew test -Dtags=smoke,db
```
Без `-Dtags` выполняются все тесты, включая `db` (так работает CI).

### 4.5 Отчёты Allure
```bash
# сгенерировать отчёт в build/allure-report
./gradlew allureReport

# сгенерировать и сразу открыть в браузере
./gradlew allureServe
```
Результаты тестов пишутся в `build/allure-results/` (настроено в `src/test/resources/allure.properties`).

## 5. Структура проекта

```
src/test/java/qa/startup/skinscan/
├── api/            # Тестовые классы (по одному на группу эндпоинтов)
│   ├── HealthCheckTest.java    # /skinScan/check-run
│   ├── AuthApiTest.java        # /skinScan/register, /skinScan/login
│   ├── RateLimitApiTest.java   # лимиты запросов с одного IP
│   ├── UserApiTest.java        # /skinScan/user/update*
│   └── PhotoApiTest.java       # /skinScan/photos*
├── clients/        # HTTP-клиенты (обёртки над REST Assured)
│   ├── AuthClient.java         # register, login, loginWithoutBody, getRegisteredUser, loginWithToken, randomForwardedFor
│   ├── UserClient.java         # update, updatePassword
│   └── PhotoClient.java        # upload, getPhotoById, getPhotoByName, getAllPhotos
├── models/         # Модели данных (records)
│   ├── User.java               # учётные данные + accessToken / authorization()
│   ├── JwtRequest.java         # тело логина: {"login", "pass"}
│   ├── JwtResponse.java        # ответ логина: type, accessToken, refreshToken
│   ├── UserRequest.java        # тело запроса регистрации/обновления
│   └── PasswordUpdateRequest.java  # тело запроса смены пароля
├── testdata/       # Загружаемые файлы (наследники UploadFile)
│   ├── UploadFile.java         # база: имя, id, MIME-тип, содержимое
│   ├── Picture.java            # изображения (PNG 1x1 в Base64), уникальные имена
│   └── Document.java           # текстовый файл — для проверки неверного формата
├── db/
│   ├── Db.java                 # доступ к БД приложения через Spring JdbcTemplate
│   ├── BcryptHash.java         # проверка формата BCrypt-хеша
│   ├── DbUserChecksTest.java   # проверки таблицы users (хеш пароля)
│   └── DbPhotoChecksTest.java  # проверки таблицы photo (статус анализа)
└── config/
    └── Config.java             # конфигурация окружения: base.url / db.*

docs/
├── test-cases/
│   └── api-test-cases.md       # тест-кейсы по каждому тесту (шаги, ожидаемые результаты)
└── bugs.md                     # баг-репорты по дефектам серверной части
```

**Ключевые принципы:**
- **Клиенты (`clients/`)** занимаются только HTTP-вызовами и помечены `@Step` — каждый вызов виден в отчёте Allure как шаг.
- **Тестовые данные (`testdata/`, `models/`) отделены от клиентов** — генерация случайных пользователей, телефонов, имён файлов и изображений вынесена отдельно.
- **`AuthClient.getRegisteredUser()`** — хелпер: создаёт пользователя со случайными данными, регистрирует его и логинит, возвращая пользователя с `accessToken`. Гарантирует, что тесты не конфликтуют между собой (суффикс из 8 символов UUID в логине/email).
- **Авторизация — JWT.** Защищённые эндпоинты требуют `Authorization: Bearer <accessToken>`; логин (`GET /skinScan/login`) принимает JSON-тело `{"login": ..., "pass": ...}` и возвращает `accessToken` и `refreshToken`. Пароль в теле `PUT /user/update` проверяется отдельно от токена.
- **`AuthClient.randomForwardedFor()`** — случайный IP в заголовке `X-Forwarded-For`, чтобы rate limit сервера не блокировал повторные запуски тестов.

## 6. Покрытие API (текущие тесты)

### 6.1 Health Check
- `GET /skinScan/check-run` — 200, статус `Успешно`, БД `PostgreSQL`, результат работы БД `1`.

### 6.2 Регистрация и вход
- `POST /skinScan/register` — 201 для нового пользователя; 201 при регистрации только с логином и паролем (email и телефон не обязательны).
- `POST /skinScan/register` — 409 при повторной регистрации того же логина.
- `POST /skinScan/register` — 400 при невалидном email, коротком пароле (< 6 символов), пустом логине или пустом пароле.
- `GET /skinScan/login` — 200 с валидными учётными данными; тело содержит `type` = `Bearer`, `accessToken` и `refreshToken`.
- `GET /skinScan/login` — 401 при неверном пароле или несуществующем пользователе; 400 без тела запроса.

### 6.3 Rate limiting
- `POST /skinScan/register` — 429 после 5 запросов с одного IP.
- `GET /skinScan/login` — 429 после 10 запросов с одного IP.

### 6.4 Обновление пользователя
- `PUT /skinScan/user/update` — 200 с валидной авторизацией.
- `PUT /skinScan/user/update` — 400 при пустом логине / невалидном email.
- `PUT /skinScan/user/update` — 401 без заголовка Authorization / с невалидным токеном.
- `PUT /skinScan/user/update` — 401 с валидным токеном, но неверным паролем в теле (пароль проверяется отдельно от JWT).
- `PUT /skinScan/user/update/{login}` — смена пароля: вход с новым паролем 200, со старым — 401.
- `PUT /skinScan/user/update/{login}` — 401 с неверным старым паролем; 400 при новом пароле < 6 символов.
- `PUT /skinScan/user/update/{login}` — 401 при попытке сменить пароль постороннего пользователя.

### 6.5 Фотографии
- `POST /skinScan/photos/upload` — 202 при успешной загрузке; 200 при повторной загрузке с тем же именем; 400 для файла неверного формата; 401 без авторизации; 202 при одинаковом имени файла у разных пользователей (имя уникально в пределах пользователя).
- `GET /skinScan/photos/{id}` — 200 с метаданными (`size_file`, `processing_time`) после завершения анализа; 502, пока анализ не завершён; 404 для несуществующего id; 400 для id, не являющегося UUID; 403 для чужого фото.
- `GET /skinScan/photos/name/{nameFile}` — 200 после анализа; 502, пока анализ не завершён; 404 для несуществующего имени и для чужого фото (поиск идёт только среди фото текущего пользователя).
- `GET /skinScan/photos` — 200 со списком id фото пользователя (у нового пользователя список пуст); 401 без авторизации.
- **Асинхронность:** после загрузки фото тесты через Awaitility ждут завершения анализа (до 60 секунд), т.к. сервер возвращает 502, пока фото в обработке.

### 6.6 Проверки БД (таг `db`)
- Таблица `users`: после регистрации пароль хранится как BCrypt-хеш (`$2[aby]$<cost>$<53 символа>`), а не открытым текстом; после смены пароля хеш обновляется.
- Таблица `photo`: после загрузки статус доходит до «Анализ завершен» (ожидание через Awaitility, до 60 секунд).

## 7. CI (GitHub Actions)

Workflow `.github/workflows/skin_scan_api.yml` («SkinScan API Tests») автоматизирует прогон и отчётность:

**Триггеры:**
- **push в `main`** — полный прогон + публикация отчёта в GitHub Pages;
- **schedule** — ежедневно в 06:00 UTC;
- **workflow_dispatch** — ручной запуск с выбором репозитория приложения и ветки.

**Шаги pipeline:**
1. PostgreSQL 16 поднимается как service-контейнер (БД `skinScan_db`, пользователь `skinScan_user`).
2. Клонируется репозиторий приложения SkinScan и запускается `./gradlew bootRun` (профиль `local`, Flyway применяет миграции автоматически). Обязательные переменные окружения приложения:
   - `JWT_SECRET` — без него приложение не стартует (`jwt.secret=${JWT_SECRET}` без значения по умолчанию);
   - `APP_ML_CLIENT_STUB_FAILURE_PROBABILITY=0` — отключает случайные сбои ML-заглушки, иначе прогон нестабилен (подробнее — `docs/bugs.md`, дефект 7).
3. Ожидание готовности по `GET /skinScan/check-run` (до 3 минут, при таймауте — артефакт с логами приложения).
4. Прогон тестов: `./gradlew cleanTest test -Dbase.url=... -Ddb.url=... -Ddb.user=... -Ddb.password=...`.
5. Сырые результаты Allure загружаются как артефакт (30 дней); при падении дополнительно выгружаются логи приложения `bootrun.log` (7 дней).
6. Отчёт генерируется с историей прогонов (history переносится из ветки `gh-pages`) и публикуется в GitHub Pages (для push в `main` и ручного запуска; для `schedule` — только прогон тестов без публикации).

**Первичная настройка (один раз):**
1. Переменная репозитория `SKINSCAN_APP` (Settings → Secrets and variables → Actions → Variables) — `owner/app-repo`.
2. Settings → Pages → Source = **GitHub Actions**.

Отчёт после прогона: `https://<owner>.github.io/qa-skin-scan/`; артефакты — во вкладке Actions.
